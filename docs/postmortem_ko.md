## 1. Pi에 너무 무거웠던 파이프라인

- **증상**: 차량이 몇 cm 전진 후 정지 반복 (07.14–17)
- **프레임별 작업**: HSV 마스크 → 선택적 침식 → Canny → Hough → 좌/우 회귀 (`fitLine`, 이후 이차 `polyfit`) → 소실점 → 진행 방향 → PID → `imshow` 창
- **해상도**: 드라이버가 모든 프레임을 1280×720으로 크기 변경 (`usb_camera_driver.cpp`) → 모든 단계가 프레임당 약 0.9 MP 처리
- **정지-출발 로직**: 여러 버전에서 차선 하나가 한 프레임만 사라져도 스로틀 0 전송
- **시도**: C++ 포팅 (lane5c), 디버그 창 제거, 단순 변형 (lane7) 모두 시간 내 준비 실패
- **수정 (07.17 밤)**: 새 640×480 카메라와 Instructables "Lane Keeping Car" 파이프라인 적용 (Hough → 좌우 평균선 1개씩 → atan 진행 방향 → 비례 조향) · 선 하나만 보여도 정지 대신 조향
- **전이된 이유**: 원본은 320×240 대상, 우리 카메라는 같은 4:3 비율의 640×480, ROI와 조향 계산이 비율 기반
- **놓친 단서**: 07.03 주최 측 조언, "Raspberry Pi 때문에 알고리즘은 단순하고 빠르게", "색상 값은 현장에서 튜닝"

## 2. 이미지 좌표를 데카르트 좌표처럼 해석

- **접근**: 허프 변환으로 뽑은 좌우 대표 차선의 기울기로 조향
- **증상**: Pure Pursuit 버전이 완전히 다른 방향으로 조향하고 움직이지 않음 (07.14) · 하이브리드 노드가 오른쪽 차선 중심에 대해 "turn left" 출력, 공식은 오른쪽 조향 (07.15)
- **원인**: 이미지 원점은 좌상단이고 y는 아래로 증가하는데 기울기를 일반 x-y 그래프처럼 해석
  - 정면 소실점이 0° 대신 약 -90° (07.14)
  - 이미지상 양수 기울기를 "음수"로 표기하고 좌회전으로 처리 (07.17 22:22)
  - 한쪽 차선만 보일 때 가파른 선일수록 크게 조향, 이미지에서 가파른 선은 차량이 정렬된 상태 (07.17)
- **맞았던 부분**: 기울기 부호와 x 위치로 좌우 차선을 나누는 분류는 처음부터 정상 (07.10 예시, 07.12 lane3)
- **수정**: 차량 좌표 변환 시 y 반전 (`img_h - vp_y`, 07.14) · 최종 노드는 기울기 대신 차선 중심 오프셋으로 조향 (`atan(x_offset / y_offset)`), 헤딩 반전 (`180 - angle`)
- **Pure Pursuit의 두 번째 원인** *(코드 분석)*: 각도를 이미지 x축 기준으로 측정 → 어느 쪽이든 한쪽으로 급조향
- **숨은 오타**: 07.18 08:21 버전의 `teering_angle = 180 - steering_angle`이 흰색 차선 경로의 미러링을 조용히 비활성화 · 13:02 레이스 버전에서 수정

## 3. 자동 모드가 차선 노드를 따라가지 않음

- **증상 (07.15 16:30)**: 모드 전환, 버튼, 수동, 자동 주행 모두 "오류 없이 아무 일도 안 됨" · 주최 측 원본 코드는 정상 동작 · 팀은 다른 팀 gamepad 의심
- **원인 중 하나 (git 이력)**: "Add joystick auto/manual mode switching" 커밋 (07.14)이 `control_node`의 `/steering`, `/throttle` 구독 제거 → 자동 모드가 차선 노드 무시 · 수동 모드 실패는 설명하지 못하며 끝내 진단 못 함
- **수정**: 07.16 구독 복구 ("Restore auto-mode subscriptions in control_node") · 같은 날 타이머도 0.2 s → 0.02 s → 0.2 s 변경
- **교훈**: `ros2 topic info /steering` 또는 `rqt_graph` 확인 시 누락된 edge 즉시 확인 가능

## 4. 최종 컨트롤러는 PD가 아니라 비례 제어

- `compute_pd_control`은 Instructables 코드 출처, 여기서 PD는 **모터 속도** 설정용이고 조향은 켜기/끄기
- 우리 노드의 조향은 `deviation / 180`에 ±8° 데드밴드 (출력 -0.23), [-0.55, 0.28] 클리핑, 차선 중심이 이미지 중심 오른쪽이면 추가 -0.39 · 실제 출력 범위는 약 -0.88~0.28이라 publish 클리핑 [-0.9, 0.7] 미적용
- PD 값은 스로틀에만 입력, `max(min(|pd|, 0.25), 0.26)`은 항상 0.26 반환 → `kp = 0.45`와 D 항 모두 출력에 영향 없음 · 붉은색 영역에서는 스로틀 고정 0.23, 조향 제한 0.3
- 정의됐지만 호출되지 않음: 노란색 차선 분기, `detective_stop_line` (출발선과 횡단보도용 흰색 픽셀 수, 불안정해서 폐기)
- 고정 스로틀이 곡선 구간에 너무 빠름: 차량이 굽은 구간에서 계속 밀려나 race 2의 차로 이탈 약 2회 및 회전 교차로 건너뜀 결정 발생
- 곡선 구간 감속 시도 이력: 소실점이 멀 때 감속(lane3, 07.12), 중심 오차가 20 px를 넘을 때 스로틀 하향(lane5, 07.16–17) · 모두 제한 시간 내 안정적으로 동작하지 않아, 팀은 약 2회 이탈을 수용하는 빠른 고정 스로틀을 최선의 절충으로 판단
- 다음 단계: 조향에 실제 PD 적용 및 조향각 또는 차선 곡률에 따라 낮아지는 스로틀 적용

## 5. 미션이 통합됐다면

- 기록: 4:52.5 = 순수 LapTIME + 차로 이탈 약 2회(각 +30 s) + 횡단보도·종료 지점 정지선 실패(각 +1 min), 대회에서 적용된 패널티 기준
- 순수 LapTIME ≈ 1:52.5 *(차로 이탈 횟수는 팀 회상 기준)*
- 회전 교차로(노란 차선)는 시간 패널티 없음 · 이탈 시 차량이 회전 교차로 진입부로 복귀 · 곡선 구간에서 이미 차로를 이탈했고 노란색 mask가 작동하지 않아 건너뛰고 바깥 순환 경로 선택
- 횡단보도·종료 정지 동작 시 *(추정)*: ≈ 2:52.5 · 초안은 존재 (흰색 픽셀 정지선 수, 수직선 횡단보도 확인, 7 s ROS 타이머, 체스보드 검출), 그러나 붙여넣은 상태로 실행된 것은 없음 (07.18 10:48–13:18)
- 순위 영향 불명 · 다른 팀 기록 미확보

## 교훈

- **대상 장비에서 먼저 측정**: 0일 차에 카메라 해상도와 프레임 시간 예산 고정, 측정으로 필요성이 보일 때만 복잡도 추가
- **가장 단순한 종단 간 드라이버 먼저**: Hough + 평균 + P 제어이면 07.14에 주행 가능했음
- **미션 조기 구현**: 각 미션은 1분 가치 · 조악한 상태 기계 버전이 정교한 차선 코드보다 유리
- **좌표계는 종이에 먼저**: 좌/우와 기울기 부호 확인용 합성 테스트 이미지 1개
- **채팅 붙여넣기 대신 버전 관리**: 약 50개 버전이 채팅으로 이동, 고정 복사본 잘림, 로컬 수정이 pull로 손실 · `main`은 07.13부터 방치, 레이스 코드는 대회 중 커밋되지 않음
